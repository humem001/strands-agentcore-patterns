# strands-agentcore-mcp — Project Conventions

Durable patterns and gotchas for this project. These apply to all code, infrastructure, and scripts regardless of which spec or task is in flight.

## Architecture at a Glance

```
User → Agent Lambda (Strands SDK + Claude Sonnet 4.5)
     → Cognito JWT (ID or access tokens)
     → AgentCore Gateway (CUSTOM_JWT authorizer)
     → MCP Target (HTTPS URL)
         → API Gateway (HTTPS endpoint, /prod/mcp)
         → MCP Server Lambda (JSON-RPC 2.0 over HTTP)
         → DynamoDB (Product_Table)
```

Region: `us-east-1`. Model: Claude Sonnet 4.5 (`us.anthropic.claude-sonnet-4-5-20250929-v1:0`) on Bedrock.
Configurable via the `BEDROCK_MODEL_ID` Lambda environment variable or the `BedrockModelId` CloudFormation parameter — no code change needed to swap models.

## Why API Gateway Sits in Front of the MCP Lambda

AgentCore Gateway's MCP target type requires an **HTTPS endpoint** to send MCP protocol requests to. Lambda has no public HTTPS endpoint on its own, so API Gateway sits in front of the MCP server Lambda to provide one. The AgentCore Gateway then forwards MCP requests (tool discovery, tool invocation) to that URL.

This is different from Smithy or OpenAPI targets, which define the API schema upfront and let the Gateway handle translation. With an MCP target, the Lambda IS the MCP server and speaks MCP protocol directly.

## Agent Control Loop (Who Chooses the Tool)

The LLM — not the Lambda — decides which tool to invoke. The Strands SDK orchestrates the loop:

1. Agent Lambda receives a user prompt and establishes an MCP client session against AgentCore Gateway
2. Strands SDK calls `tools/list` over MCP to fetch the tool catalog (name, description, `inputSchema`)
3. Strands SDK passes the prompt, system prompt, and tool schemas to Claude Sonnet 4.5 via Bedrock
4. The **model** returns a tool-use decision (which tool to call and with which arguments) or a final answer
5. If a tool call was requested, Strands SDK issues `tools/call` over MCP; the Gateway forwards to the MCP server Lambda, which executes the tool and returns a result
6. The tool result is fed back into the model; repeat until the model returns a final answer
7. Agent Lambda returns the final conversational answer to the user

Rule: the Agent Lambda never hard-codes which tool to call. Tool selection is entirely model-driven based on the user's prompt and the schemas discovered at runtime.

## CloudFormation Property Casing (Gotchas)

These have bitten us before — get them right the first time:

- `AuthorizerConfiguration.CustomJWTAuthorizer` — `JWT` in all caps, NOT `CustomJwtAuthorizer`
- `RoleArn` on the Gateway, NOT `ExecutionRoleArn`
- `AllowedAudience` under `CustomJWTAuthorizer`, NOT `Audience`
- `CredentialProviderConfigurations` as an **array**, NOT a top-level `CredentialProviderType` scalar
- `DiscoveryUrl` must end with `/.well-known/openid-configuration`

## AgentCore Gateway — MCP Target Shape

```yaml
McpTarget:
  Type: AWS::BedrockAgentCore::GatewayTarget
  Properties:
    GatewayIdentifier: !Ref AgentCoreGateway
    Name: mcp-server-target
    CredentialProviderConfigurations:
      - CredentialProviderType: GATEWAY_IAM_ROLE
    TargetConfiguration:
      Mcp:
        McpServer:
          EndpointUrl: !Sub 'https://${McpApi}.execute-api.${AWS::Region}.amazonaws.com/prod/mcp'
```

`GATEWAY_IAM_ROLE` removes the need for any credential-provider CLI dance.

## Gateway Execution Role — Required Permissions

Four AgentCore ARN patterns plus API Gateway invoke:

- `bedrock-agentcore:*` on:
  - `arn:aws:bedrock-agentcore:{region}:{account}:token-vault/default`
  - `arn:aws:bedrock-agentcore:{region}:{account}:token-vault/default/apikeycredentialprovider/*`
  - `arn:aws:bedrock-agentcore:{region}:{account}:workload-identity-directory/default`
  - `arn:aws:bedrock-agentcore:{region}:{account}:workload-identity-directory/default/workload-identity/{gateway-name}-*`
- `execute-api:Invoke` on `arn:aws:execute-api:{region}:{account}:{McpApi}/*/*/*`

Never grant wildcard `*` on all AWS resources.

## JWT Validation Rules

All three are mandatory and reused as-is from `src/shared/jwt_utils.py`:

- Accept both `token_use: access` and `token_use: id`
- Disable audience verification locally (`verify_aud=False`) — the Gateway enforces audience via `AllowedAudience`
- Extract username from the `cognito:username` claim (NOT `username`, NOT `sub`)

If a JWT is missing, expired, or signature-invalid, Agent Lambda returns an auth error without calling the Gateway.

## Lambda Packaging — Two-Step pip3 Install (CRITICAL)

`--only-binary=:all:` with `--platform` silently skips pure-Python packages. Always do both steps:

```bash
# Step 1: binary packages
pip3 install --target "$DIR" \
  --platform manylinux2014_x86_64 --python-version 3.12 \
  --only-binary=:all: -r requirements.txt

# Step 2: pure-Python packages (skipped by step 1)
pip3 install --target "$DIR" \
  --platform manylinux2014_x86_64 --python-version 3.12 \
  --only-binary=:all: --no-deps \
  requests urllib3 charset-normalizer idna certifi PyJWT cryptography cffi mcp
```

Additional rules:

- Do NOT remove `.dist-info` directories — OpenTelemetry needs them
- Preserve the `src/` prefix inside the zip so `src.agent.handler.lambda_handler` and `src.mcp_server.handler.lambda_handler` resolve
- If the zip exceeds 50 MB, upload to S3 and deploy via S3 reference instead of inline

## Deploy Script Patterns

- Use `pip3`, never `pip`
- Stack create vs update: case-insensitive match against the `DOES_NOT_EXIST` string returned by `aws cloudformation describe-stacks`
- If the stack is in `ROLLBACK_COMPLETE`, delete it and wait for completion before re-creating
- Use `$$`-based PID temp file names (e.g. `/tmp/foo.$$.json`), NOT `mktemp` suffix templates — macOS `mktemp` doesn't accept them
- Validate the CloudFormation template before any other action
- Generate `scripts/test.sh` with deployment values baked in as literal strings; never use nested `echo` emitting JSON

## MCP Server Lambda — Protocol Shape

- JSON-RPC 2.0 over HTTP via API Gateway `AWS_PROXY` integration
- Handle `tools/list` → return tool catalog with `name`, `description`, `inputSchema`
- Handle `tools/call` → dispatch to the named tool, return `result.content`
- Always return HTTP 200 for JSON-RPC responses (including JSON-RPC error objects); `Content-Type: application/json`
- JSON-RPC error codes: `-32700` parse error, `-32601` method not found, `-32602` invalid params, `-32603` internal error

## Product Tool Contract

Table: `Product_Table` — partition key `category` (S), sort key `productId` (S), `PAY_PER_REQUEST` billing.

- `list_products(category?)` — Scan if no category, Query if category provided
- `get_product(category, productId)` — GetItem; return not-found result (not an error) if missing
- `put_product(category, productId, name, price)` — PutItem; overwrites on conflict

Round-trip property: `put_product(x)` followed by `get_product(x.category, x.productId)` returns `x`.

## Observability

Both Lambdas emit structured JSON logs via `src/shared/logging_utils.py`. MCP server logs the JSON-RPC `method` on every request and the tool `name` on tool calls.
