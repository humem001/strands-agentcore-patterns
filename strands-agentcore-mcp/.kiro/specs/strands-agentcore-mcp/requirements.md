# Requirements Document

## Introduction

This feature delivers a serverless AI agent that answers user prompts by invoking product-management tools exposed through AWS Bedrock AgentCore Gateway using an MCP (Model Context Protocol) target type. An Agent Lambda authenticates users via Cognito, connects to the AgentCore Gateway over MCP, and invokes tools backed by a custom MCP server Lambda fronted by API Gateway and backed by DynamoDB.

The architecture reuses authentication, agent runtime, and gateway patterns from the prior `strands-agentcore-smithy` project, but replaces the Smithy target with an MCP target. This requires a new HTTPS-accessible MCP server (API Gateway + Lambda + DynamoDB) because the MCP target type in AgentCore Gateway forwards MCP JSON-RPC requests to an HTTPS URL.

## Glossary

- **Agent_Lambda**: The AWS Lambda function that hosts the Strands SDK agent and acts as the entry point for user prompts.
- **MCP_Server_Lambda**: The AWS Lambda function that implements the MCP protocol over JSON-RPC and serves product-management tools.
- **MCP_Api**: The Amazon API Gateway REST API that exposes the MCP_Server_Lambda over HTTPS at a single POST endpoint.
- **AgentCore_Gateway**: The AWS Bedrock AgentCore Gateway resource configured with a `CUSTOM_JWT` authorizer and an MCP target pointing at MCP_Api.
- **MCP_Target**: The AWS Bedrock AgentCore GatewayTarget resource of target type `Mcp` referencing the MCP_Api HTTPS URL.
- **Gateway_Execution_Role**: The IAM role assumed by AgentCore_Gateway when invoking MCP_Api and accessing AgentCore resources.
- **Cognito_User_Pool**: The Amazon Cognito User Pool used to authenticate users and issue JWTs.
- **Cognito_User_Pool_Client**: The Cognito User Pool Client configured for `USER_PASSWORD_AUTH`.
- **Product_Table**: The Amazon DynamoDB table storing product items keyed by `category` (partition) and `productId` (sort).
- **System**: The full deployed feature comprising Agent_Lambda, MCP_Server_Lambda, MCP_Api, AgentCore_Gateway, MCP_Target, Cognito_User_Pool, Gateway_Execution_Role, and Product_Table.
- **Deploy_Script**: The `scripts/deploy.sh` script that validates the template, packages Lambda code, deploys the CloudFormation stack, seeds data, creates a test user, and generates the test script.
- **Test_Script**: The `scripts/test.sh` script generated by Deploy_Script with baked-in deployment values for end-to-end testing.
- **MCP_Tool**: A named operation exposed by MCP_Server_Lambda via the MCP protocol (`list_products`, `get_product`, `put_product`).
- **JWT**: A JSON Web Token issued by Cognito_User_Pool, accepted by AgentCore_Gateway's `CUSTOM_JWT` authorizer and validated by Agent_Lambda.

## Requirements

### Requirement 1: User Authentication via Cognito

**User Story:** As an end user, I want to authenticate with a username and password, so that I can obtain a JWT that authorizes my requests to the agent.

#### Acceptance Criteria

1. THE Cognito_User_Pool SHALL be provisioned by CloudFormation with a User Pool Client configured for the `USER_PASSWORD_AUTH` authentication flow.
2. WHEN Deploy_Script runs successfully, THE System SHALL create a test user in Cognito_User_Pool with a confirmed password.
3. WHEN Agent_Lambda receives a request containing a Cognito-issued JWT, THE Agent_Lambda SHALL validate the token's signature against the Cognito_User_Pool JSON Web Key Set.
4. WHERE the token's `token_use` claim is either `access` or `id`, THE Agent_Lambda SHALL accept the token as valid.
5. WHEN validating a JWT, THE Agent_Lambda SHALL set `verify_aud` to `False` so that audience verification is delegated to AgentCore_Gateway.
6. WHEN extracting the authenticated username from a JWT, THE Agent_Lambda SHALL read the `cognito:username` claim.
7. IF a JWT is missing, expired, or has an invalid signature, THEN THE Agent_Lambda SHALL return an authentication error response without invoking AgentCore_Gateway.

### Requirement 2: Agent Lambda Runtime

**User Story:** As an end user, I want my natural-language prompt handled by a Claude-powered agent, so that I get conversational answers grounded in product data.

#### Acceptance Criteria

1. THE Agent_Lambda SHALL be deployed with the Strands SDK and configured to use the `Claude 3 Sonnet` model on Amazon Bedrock in `us-east-1`.
2. WHEN Agent_Lambda receives a validated user prompt, THE Agent_Lambda SHALL establish an MCP client session against AgentCore_Gateway using the user's JWT as the bearer credential.
3. WHEN invoking AgentCore_Gateway, THE Agent_Lambda SHALL discover available MCP_Tools via the MCP `tools/list` operation before completing the first model turn.
4. WHEN Agent_Lambda invokes the Bedrock model, THE Agent_Lambda SHALL pass the discovered MCP_Tool schemas to the model so that the model (not the Lambda) decides which MCP_Tool to call.
5. WHEN the Bedrock model returns a tool-use decision naming an MCP_Tool and arguments, THE Agent_Lambda SHALL invoke that tool through the MCP client session and return the tool's response to the model for the next turn.
6. THE Agent_Lambda SHALL repeat the model-turn-then-tool-call loop until the model returns a final conversational answer, then return that answer to the caller.
7. THE Agent_Lambda SHALL use a system prompt that describes the available MCP_Tools (`list_products`, `get_product`, `put_product`) and instructs the agent to respond conversationally based on tool results.
8. IF the MCP client session to AgentCore_Gateway fails to establish, THEN THE Agent_Lambda SHALL return an error response describing the gateway connectivity failure.
9. THE Agent_Lambda SHALL reuse, without modification, the `src/agent/handler.py`, `src/agent/agent_processor.py`, `src/agent/strands_client.py`, and all files under `src/shared/` from the prior `strands-agentcore-smithy` project, except for updating the system prompt.

### Requirement 3: AgentCore Gateway with CUSTOM_JWT Authorizer

**User Story:** As a platform owner, I want AgentCore Gateway to authorize requests using Cognito JWTs, so that only authenticated users can reach the MCP tools.

#### Acceptance Criteria

1. THE AgentCore_Gateway SHALL be provisioned as an `AWS::BedrockAgentCore::Gateway` resource with an `AuthorizerConfiguration.CustomJWTAuthorizer` block.
2. THE `CustomJWTAuthorizer` configuration SHALL set `DiscoveryUrl` to the Cognito_User_Pool's OpenID Connect discovery URL ending in `/.well-known/openid-configuration`.
3. THE `CustomJWTAuthorizer` configuration SHALL set `AllowedAudience` to the Cognito_User_Pool_Client's App Client ID.
4. THE AgentCore_Gateway SHALL reference Gateway_Execution_Role via the `RoleArn` property.
5. IF a request reaches AgentCore_Gateway without a valid JWT whose audience matches `AllowedAudience`, THEN THE AgentCore_Gateway SHALL reject the request before invoking MCP_Target.

### Requirement 4: MCP Target Pointing to API Gateway

**User Story:** As a platform owner, I want AgentCore Gateway to forward MCP requests to my custom MCP server over HTTPS, so that tool execution runs in my own Lambda.

#### Acceptance Criteria

1. THE MCP_Target SHALL be provisioned as an `AWS::BedrockAgentCore::GatewayTarget` resource with `TargetConfiguration.Mcp.McpServer.EndpointUrl` set to the HTTPS invoke URL of MCP_Api at path `/prod/mcp`.
2. THE MCP_Target SHALL declare `CredentialProviderConfigurations` as an array containing a single entry with `CredentialProviderType` equal to `GATEWAY_IAM_ROLE`.
3. THE MCP_Target SHALL reference AgentCore_Gateway via `GatewayIdentifier`.
4. WHEN AgentCore_Gateway receives an authorized MCP request, THE AgentCore_Gateway SHALL forward the request to the `EndpointUrl` declared on MCP_Target using the Gateway_Execution_Role credentials.

### Requirement 5: Gateway Execution Role Permissions

**User Story:** As a platform owner, I want the gateway's IAM role scoped to exactly the resources it needs, so that it can reach AgentCore resources and invoke MCP_Api without overprivileging.

#### Acceptance Criteria

1. THE Gateway_Execution_Role SHALL trust the `bedrock-agentcore.amazonaws.com` service principal.
2. THE Gateway_Execution_Role SHALL grant `bedrock-agentcore:*` on the following four ARN patterns: `token-vault/default`, `token-vault/default/apikeycredentialprovider/*`, `workload-identity-directory/default`, and `workload-identity-directory/default/workload-identity/{gateway-name}-*`.
3. THE Gateway_Execution_Role SHALL grant `execute-api:Invoke` on `arn:aws:execute-api:{region}:{account}:{McpApi}/*/*/*`.
4. THE Gateway_Execution_Role SHALL NOT grant wildcard permissions on all AWS resources.

### Requirement 6: MCP Server Lambda — Protocol Handling

**User Story:** As an agent developer, I want the MCP server Lambda to speak MCP JSON-RPC over HTTP, so that AgentCore Gateway can discover and invoke tools through it.

#### Acceptance Criteria

1. WHEN MCP_Server_Lambda receives a request from API Gateway, THE MCP_Server_Lambda SHALL parse the body as a JSON-RPC 2.0 request.
2. WHEN the JSON-RPC `method` is `tools/list`, THE MCP_Server_Lambda SHALL return a JSON-RPC response whose `result.tools` array contains entries for `list_products`, `get_product`, and `put_product`, each with `name`, `description`, and `inputSchema` fields.
3. WHEN the JSON-RPC `method` is `tools/call` and the `params.name` names a registered MCP_Tool, THE MCP_Server_Lambda SHALL execute the named tool with `params.arguments` and return a JSON-RPC response whose `result.content` contains the tool's output.
4. IF the JSON-RPC `method` is `tools/call` and `params.name` is not a registered MCP_Tool, THEN THE MCP_Server_Lambda SHALL return a JSON-RPC error response with code `-32601` (method not found) and a descriptive message.
5. IF the request body is not valid JSON-RPC 2.0, THEN THE MCP_Server_Lambda SHALL return a JSON-RPC error response with code `-32700` (parse error).
6. WHEN MCP_Server_Lambda returns any response to API Gateway, THE MCP_Server_Lambda SHALL set the HTTP status to `200` for successful JSON-RPC responses (including JSON-RPC error objects) and `Content-Type` to `application/json`.
7. FOR ALL valid MCP JSON-RPC requests handled by MCP_Server_Lambda, serializing the response object to JSON and deserializing it SHALL produce an equivalent object (round-trip property).

### Requirement 7: MCP Server Lambda — Product Tools

**User Story:** As an end user, I want to list, read, and write products through the agent, so that I can manage product data conversationally.

#### Acceptance Criteria

1. THE MCP_Tool `list_products` SHALL accept an optional `category` string argument and return a list of products from Product_Table, filtered by `category` when provided.
2. THE MCP_Tool `get_product` SHALL accept required `category` and `productId` string arguments and return the matching Product_Table item.
3. IF `get_product` is invoked with a `category`/`productId` pair that does not exist in Product_Table, THEN THE MCP_Server_Lambda SHALL return a tool result indicating that the product was not found.
4. THE MCP_Tool `put_product` SHALL accept required `category`, `productId`, `name`, and `price` arguments and write the item to Product_Table.
5. WHEN `put_product` is invoked with the same `category`/`productId` as an existing item, THE MCP_Server_Lambda SHALL overwrite the existing item in Product_Table.
6. IF a tool is invoked with arguments that do not match its declared `inputSchema`, THEN THE MCP_Server_Lambda SHALL return a JSON-RPC error response with code `-32602` (invalid params).
7. FOR ALL product items written via `put_product`, a subsequent `get_product` call with the same `category` and `productId` SHALL return the item that was written (round-trip property).

### Requirement 8: API Gateway HTTPS Endpoint

**User Story:** As a platform owner, I want the MCP server Lambda exposed via a stable HTTPS URL, so that AgentCore Gateway can reach it as an MCP target.

#### Acceptance Criteria

1. THE MCP_Api SHALL be provisioned as an `AWS::ApiGateway::RestApi` resource with a `/mcp` resource and a `POST` method integrated with MCP_Server_Lambda using `AWS_PROXY` integration.
2. THE MCP_Api SHALL be deployed to a stage named `prod` via `AWS::ApiGateway::Deployment` and `AWS::ApiGateway::Stage` resources.
3. THE MCP_Api SHALL grant Gateway_Execution_Role permission to invoke the `POST /mcp` method via a Lambda resource-based permission.
4. WHEN a `POST` request is sent to `/prod/mcp`, THE MCP_Api SHALL invoke MCP_Server_Lambda with the request body and return the Lambda's response unchanged.

### Requirement 9: MCP Server Lambda IAM Role

**User Story:** As a platform owner, I want the MCP server Lambda scoped to only the DynamoDB table it needs, so that its blast radius is minimized.

#### Acceptance Criteria

1. THE MCP_Server_Lambda SHALL assume a dedicated IAM role that trusts the `lambda.amazonaws.com` service principal.
2. THE MCP_Server_Lambda IAM role SHALL grant `dynamodb:GetItem`, `dynamodb:PutItem`, `dynamodb:Query`, and `dynamodb:Scan` scoped to the Product_Table ARN only.
3. THE MCP_Server_Lambda IAM role SHALL grant `logs:CreateLogGroup`, `logs:CreateLogStream`, and `logs:PutLogEvents` sufficient to write CloudWatch logs.
4. THE MCP_Server_Lambda IAM role SHALL NOT grant DynamoDB permissions on any table other than Product_Table.

### Requirement 10: DynamoDB Product Table

**User Story:** As a platform owner, I want product data stored in a managed table, so that the MCP server Lambda can read and write items without managing storage.

#### Acceptance Criteria

1. THE Product_Table SHALL be provisioned as an `AWS::DynamoDB::Table` with partition key `category` (string) and sort key `productId` (string).
2. THE Product_Table SHALL use on-demand (`PAY_PER_REQUEST`) billing mode.
3. WHEN Deploy_Script runs successfully, THE System SHALL seed Product_Table with at least three sample products spanning at least two distinct categories.

### Requirement 11: Lambda Packaging

**User Story:** As an operator, I want Lambda deployment packages to include all runtime dependencies correctly, so that the functions do not fail at cold start due to missing modules.

#### Acceptance Criteria

1. WHEN Deploy_Script packages a Lambda, THE Deploy_Script SHALL run `pip3 install` in two steps: first with `--only-binary=:all:` against `requirements.txt` for binary packages, then with `--only-binary=:all: --no-deps` for the pure-Python packages `requests`, `urllib3`, `charset-normalizer`, `idna`, `certifi`, `PyJWT`, `cryptography`, `cffi`, and `mcp`.
2. THE Deploy_Script SHALL pass `--platform manylinux2014_x86_64` and `--python-version 3.12` to both `pip3 install` invocations.
3. THE Deploy_Script SHALL NOT remove any `.dist-info` directories from the packaged dependencies.
4. THE Deploy_Script SHALL preserve the `src/` prefix inside the Lambda zip so that CloudFormation handler paths of the form `src.agent.handler.lambda_handler` and `src.mcp_server.handler.lambda_handler` resolve correctly.
5. IF a packaged zip exceeds 50 MB, THEN THE Deploy_Script SHALL upload the zip to S3 and deploy the Lambda via S3 reference instead of inline upload.

### Requirement 12: CloudFormation Property Casing

**User Story:** As an operator, I want CloudFormation property names to follow the exact casing required by the AgentCore service, so that stack creation does not fail on validation errors.

#### Acceptance Criteria

1. THE CloudFormation template SHALL use the property name `CustomJWTAuthorizer` (with `JWT` in all capitals) under `AuthorizerConfiguration`.
2. THE CloudFormation template SHALL use the property name `RoleArn` on AgentCore_Gateway, not `ExecutionRoleArn`.
3. THE CloudFormation template SHALL use the property name `AllowedAudience` under `CustomJWTAuthorizer`, not `Audience`.
4. THE CloudFormation template SHALL declare `CredentialProviderConfigurations` as an array on MCP_Target, not a top-level `CredentialProviderType` scalar.
5. THE CloudFormation template SHALL set `DiscoveryUrl` to a value ending with `/.well-known/openid-configuration`.

### Requirement 13: Deploy Script Lifecycle

**User Story:** As an operator, I want a one-command deployment that handles fresh installs and updates, so that I can iterate quickly.

#### Acceptance Criteria

1. WHEN Deploy_Script starts, THE Deploy_Script SHALL validate the CloudFormation template before any other action.
2. WHEN Deploy_Script determines whether to create or update the stack, THE Deploy_Script SHALL perform a case-insensitive match against the `DOES_NOT_EXIST` pattern returned by the AWS CLI.
3. IF the existing stack is in `ROLLBACK_COMPLETE` state, THEN THE Deploy_Script SHALL delete the stack and wait for deletion to complete before creating it again.
4. THE Deploy_Script SHALL use `pip3` rather than `pip` for all Python dependency installations.
5. THE Deploy_Script SHALL create temporary files using `$$`-based PID names rather than `mktemp` suffix templates, so that it runs on macOS without GNU coreutils.
6. WHEN Deploy_Script completes successfully, THE Deploy_Script SHALL write a Test_Script to `scripts/test.sh` with deployment values baked in as literal strings, without using nested `echo` commands that emit JSON.
7. THE generated Test_Script SHALL accept an optional prompt argument on the command line and default to a predefined prompt when no argument is provided.

### Requirement 14: Observability

**User Story:** As an operator, I want structured logs from both Lambdas, so that I can diagnose failures across the agent and MCP server.

#### Acceptance Criteria

1. THE Agent_Lambda SHALL emit structured JSON logs to CloudWatch for each received request and each tool invocation, using the shared logging utilities from `src/shared/logging_utils.py`.
2. THE MCP_Server_Lambda SHALL emit a structured JSON log entry to CloudWatch for each incoming JSON-RPC request and each tool execution, including the JSON-RPC `method` and, when applicable, the tool `name`.
3. IF MCP_Server_Lambda encounters an exception while executing a tool, THEN THE MCP_Server_Lambda SHALL log the exception and return a JSON-RPC error response with code `-32603` (internal error).
